# `site/` — the public omega-leaderboard site

Static GitHub Pages site for the machine-checked matrix-multiplication-exponent leaderboard.
Plain HTML + one CSS file, **no JavaScript, no framework, no external assets**; generated by
stdlib-only Python (>= 3.9). Dark mode via `prefers-color-scheme`.

## Build

```bash
python3 site/extract_frontier.py     # Frontier.lean -> site/frontier.json  (committed)
python3 site/generate.py             # frontier.json + history.json + notes/ -> site/_site/
```

Output lands in `site/_site/` (gitignored): `index.html`, `scoreboard.html`, `contribute.html`,
`about.html`, `style.css`, `records.json` (the merged data, republished verbatim for bots and
badges), and `.nojekyll`. Open `site/_site/index.html` in a browser to preview.

## Data flow

```
Frontier.lean ── extract_frontier.py ──> frontier.json ─┐   (committed record: constant,
                                                        │    endpoint theorem, fingerprints)
history.json  ──────────────────────────────────────────┤   (published record history +
                                                        │    formalized ladder + conditional
notes/<slug>/note.tex  (linked when present) ───────────┤    tracks; hand-maintained)
                                                        ▼
                                              generate.py ──> site/_site/*.html
```

**`Frontier.lean` is the source of truth and is never edited by anything in this directory.**
`extract_frontier.py` is read-only and deliberately brittle: it parses exactly two load-bearing
line shapes (`def frontierConstant : ℚ := a / b` and the single `exact <endpoint> K` inside
`theorem frontier`), plus the `#assert_axioms` / `#assert_statement_fingerprint` lines. If the
Frontier owner reformats those lines, extraction FAILS with a non-zero exit instead of letting
the public site drift. `extract_frontier.py --check` verifies the committed `frontier.json`
still matches `Frontier.lean` — CI should run it on every PR (see `pages.yml.draft`).

`generate.py` additionally fails the build if:

* `frontier.json` is stale relative to `Frontier.lean`;
* any formalized row of `history.json` names a Lean module that does not exist, or a declaration
  not present in that module (content-accuracy gate);
* any emitted page fails an `html.parser` round-trip (unbalanced tags) or contains a dangling
  local link.

## Optional convention for `Frontier.lean` (proposed, not required)

The extractor prefers, when present, a machine-readable block inside the module docstring
between sentinel lines that no Lean syntax collides with:

```
<<<FRONTIER-JSON
{ "schema": 1,
  "records": [
    { "slug": "omega-2p3872", "class": "unconditional",
      "constant": "1492/625", "decimal": "2.3872",
      "theorem": "AlgebraicComplexity.Examples.coppersmithWinograd_firstPower_omega_lt",
      "file": "AlgebraicComplexity/Examples/CoppersmithWinogradFirstPower.lean",
      "date": "2026-08-28", "supersedes": null, "obligations": [] } ] }
FRONTIER-JSON>>>
```

Every `theorem` named in the block must also appear in the Lean text *outside* the block (the
JSON cannot satisfy its own check). The block is a proposal that `Frontier.lean` has not adopted; the
pinned regexes work today and fail loudly.

## Content-accuracy rules

* Everything the site claims as *formalized* traces to a Lean declaration in this repository,
  checked by the generator at build time.
* Literature-only entries are visibly marked ("literature — not formalized here") everywhere.
* Conditional tracks (proved implications with named unproved `Prop` obligations) are always
  labeled "conditional — not a record" and never rendered as bounds.
* The "Honest project status" section on the About page is kept current by hand; it must never
  claim a record the tree does not have.

## Updating

* **A record lands** (`Frontier.lean` changes): run the two build commands, commit the refreshed
  `frontier.json`. The hero number, scoreboard, chart, and pending-upgrade chip update
  automatically.
* **The published literature moves**: add a row to `history.json` `records` (status
  `literature`).
* **A bound is formalized**: move/extend its `history.json` entry (status `formalized`) and add
  a `formalized_ladder` row; the generator will refuse to build until the named declaration
  really exists in the named module.
* **A note is added** under `notes/<slug>/`: rows with that `note_slug` link it automatically
  (a committed `note.pdf` is preferred over `note.tex` if the maintainers decide to commit
  PDFs).

## Deployment

`pages.yml.draft` in this directory is the Pages workflow **draft**; deploying means copying it to
`.github/workflows/pages.yml` and setting Settings → Pages → Source to "GitHub Actions". Until
then the site builds and previews locally with the two commands above.

## Design

Modeled on bbchallenge.org / the Equational Theories Project / the FLT blueprint: the record is
the hero, the trust links sit directly under it, and the timeline chart carries two visually
distinct tracks (published literature vs formalized-here) plus dashed-outline conditional
markers so status is never color-alone. Single accent color, neutral inks, axis-labeled inline
SVG, native `<title>` tooltips, no chartjunk, no JS.
